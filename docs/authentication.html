Sign-in, end to end

The backend's Identity module owns accounts and sessions. The Next.js server stands between it and the browser, so page JavaScript never holds a backend token. The one exception is the short-lived chat token the browser needs for the chat service.

Who holds what

Email and password

The session token is a random string, not a JWT. Postgres stores only its SHA-256, so a leaked table holds no usable tokens. Sessions end 7 days after sign-in.

Google, GitHub and enterprise SSO

The API runs the whole OAuth / OpenID Connect flow and Next only relays it. State, nonce and the PKCE verifier stay in the API's database; the browser carries only a flow id in the oauth_flow cookie.

  • A provider's email links to an existing account only if that account's email is verified. Password sign-ups never are, so they get account_exists and connect the provider from Login & security.
  • SSO picks the connection from the email's domain (acme.test goes to Keycloak).
  • You can't disconnect your last way to sign in.

Chat tokens

The browser connects to the chat hub directly, so it needs a credential the chat service can check without asking the API.

Service-to-service keys

Calls between services carry no user. Each carries a secret the AppHost generates and keeps in user secrets.

Mock mode

With DATA_SOURCE=mock, getAuthGateway() swaps in a mock: any valid email and password signs in, and the /auth/mock-provider page plays every provider. The cookie works the same way, so pages can't tell the difference.
