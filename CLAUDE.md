# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository Layout

Monorepo:
- `frontend/` — Next.js app. **All frontend commands run from `frontend/`, and all frontend paths below are relative to `frontend/`.**
- `backend/` — ASP.NET Core (.NET 10) modular monolith orchestrated by Aspire 13.6. Solution `backend/Airbnb.slnx`: `src/Airbnb.AppHost` (Aspire), `src/Airbnb.Api` (host), `src/Airbnb.ServiceDefaults`, `src/Airbnb.SharedKernel`, `src/Airbnb.MigrationService`, `src/Airbnb.Functions` (the photo-processor Azure Function), modules (`src/Modules/<Name>`: Stays, Experiences, Services, Hosts, Reviews, Identity, Bookings, Media, Insights), module Contracts projects (`src/Modules/<Name>/Airbnb.Modules.<Name>.Contracts`: plain interfaces and records other modules may reference); tests in `tests/Airbnb.UnitTests`, `tests/Airbnb.ArchitectureTests`, `tests/Airbnb.Api.Tests` (integration), `tests/Airbnb.AppHost.Tests` (Aspire smoke test). SDK and test runner pinned by `backend/global.json`. Design: `docs/superpowers/specs/2026-09-26-backend-modular-monolith-design.md`.
- `services/notifications/` — the notification microservice: its own solution (`Airbnb.Notifications.slnx`, own `global.json`, `Directory.Build.props`, `Directory.Packages.props`), sharing only `backend/src/Airbnb.ServiceDefaults`; run by the backend AppHost. Commands from `services/notifications`: `dotnet test` (Testcontainers: Postgres, LavinMQ, Mailpit).
- `services/payments/` — the payment microservice, same shape (`Airbnb.Payments.slnx`, own props, shares only ServiceDefaults; run by the backend AppHost). Commands from `services/payments`: `dotnet test` (Testcontainers: Postgres, LavinMQ).
- `services/chat/` — the chat microservice, same shape (`Airbnb.Chat.slnx`, own props, shares only ServiceDefaults; run by the backend AppHost as two instances behind the YARP `gateway`). Commands from `services/chat`: `dotnet test` (Testcontainers: MongoDB, Redis; the service on real Kestrel so the hub runs over WebSockets).
- `services/assistant/` — the smart chat box's assistant, same shape (`Airbnb.Assistant.slnx`, own props, shares only ServiceDefaults; run by the backend AppHost on its Ollama model). Commands from `services/assistant`: `dotnet test` (no containers: a scripted `IChatClient` or a fake Ollama endpoint, and a fake catalog).
- `docs/` — specs and plans (repo root).
- `.devcontainer/` — Linux dev container (docker-in-docker, Node 24, the Aspire CLI pinned in `postCreateCommand` to the AppHost's Aspire version) for Macs older than macOS 15, which can't run Aspire's orchestrator, and for Codespaces. .NET builds go to `$ArtifactsPath` (`/home/vscode/artifacts`), not `bin/`/`obj/`, and `frontend/node_modules`, `frontend/.next` and `~/.microsoft` (user secrets) are volumes: sharing them with the host breaks the other side.

## Architecture

### Technology Stack
- **Next.js 16 App Router** + **React 19** + **TypeScript strict mode**
- **Tailwind CSS v4** with a custom `@theme` block in `app/globals.css` — all design tokens are CSS custom properties there, not `tailwind.config.js`
- **TanStack Query v5** for server state on the client
- **Zod v4** for API response validation
- **Vitest** + **React Testing Library** for unit/component tests; **Playwright** for E2E

### Design Token System
`frontend/DESIGN.md` is the source of truth for the visual design. All tokens are encoded in `frontend/app/globals.css`:
- **Colors:** `bg-rausch`, `text-ink`, `bg-canvas`, `border-hairline`, etc.
- **Typography:** CSS component classes `.text-display-xl`, `.text-body-md`, `.text-caption`, etc. (not Tailwind utility classes)
- **Radii:** `rounded-sm` (8px), `rounded-md` (14px), `rounded-full`
- **Shadow:** single tier `shadow-airbnb`
- **Breakpoints:** `md` 744px, `lg` 1128px, `xl` 1440px (DESIGN.md); width caps `max-w-listing` (1440) and `max-w-editorial` (1280)

Always use these named tokens rather than arbitrary Tailwind values.

### Data Layer (bottom-up)

```
lib/data/              Static mock data arrays (listings, hosts, reviews, cities, experiences, services)
lib/repositories/      Repository interfaces + getRepositories() (index.ts) — the DATA_SOURCE switch for catalog data;
                       listings/hosts are combined with host-created listings and host profiles (combined.ts);
                       wishlists, host listings and host profiles are in-memory mocks in both data modes; bookings are an in-memory mock in mock mode and `http/http-booking-repository.ts` in api mode (forwards the session cookie's token as the bearer)
  mock/                mock*Repository implementations over lib/data (plus the in-memory wishlist/booking stores)
  http/                apiFetch + createHttpRepositories(API_HTTP) — the .NET API, Zod-validated
lib/api/envelope.ts    ApiResponse<T> type + ok()/fail() helpers
app/api/*/route.ts     GET /api/{listings,experiences,services} — call getRepositories()
lib/api-client/        fetch* functions + Zod schemas validating the envelope
lib/hooks/             TanStack Query wrappers (useListings, …)
lib/auth/              session.ts (session cookie: the gateway token), gateway.ts (getAuthGateway: mock-gateway.ts / http-gateway.ts), client-ip.ts, get-session.ts (server: getSession/requireSession/getSessionToken), next-path.ts,
                       oauth-flow.ts (the oauth_flow cookie), oauth-errors.ts (callback error codes → fixed text), mock-external.ts (mock mode's providers, flows and connections), sign-in-options.ts
app/api/auth|wishlists|bookings/   session-guarded route handlers (401 envelope without a session);
                       auth/oauth/start (POST), auth/callback/[provider] (GET, a 303), auth/connections/[provider] (DELETE)
lib/host/              host listing options (cities, photo gallery, amenities), hostListingInputSchema, listing-input helpers
lib/search/match-listing.ts   matchesFilters — the one set of search filter rules (seed and host listings)
```

- `DATA_SOURCE=mock|api` (server-only, default `mock`; `api` needs `API_HTTP`) selects the implementations. Server code gets data only through `getRepositories()`; ESLint forbids importing `repositories/mock/*` outside `lib/repositories/`.
- `lib/data-source.ts` (`dataSource()`) is the one `DATA_SOURCE` parser.
- Auth goes through `getAuthGateway()` (`lib/auth/gateway.ts`): mock accounts in mock mode, the backend Identity module in api mode; the `session` cookie holds the gateway's token. `lib/auth/client-ip.ts` forwards the LAST `x-forwarded-for` entry as the browser IP (assumes a proxy in front of Next appends it). In api mode a backend outage while reading a session reads as logged out.
- Every `app/api/**/route.ts` export is wrapped in `withErrorEnvelope` (`lib/api/request.ts`).
- `lib/repositories/index.ts` and `lib/auth/gateway.ts` import `server-only` (aliased to an empty module in Vitest).
- Server components (detail pages, the homepage's cities) call `getRepositories()` directly; client components fetch the Next `/api/*` route handlers, which call it too.
- Auth is a mock in mock mode only (any valid email/password logs in); in api mode the backend Identity module owns accounts. Either way an httpOnly `session` cookie holds the gateway's token. Wishlists are frontend in-memory mocks in both `DATA_SOURCE` modes; bookings are too in mock mode, but the backend Bookings module serves them in api mode. Client code reads the session and wishlist hearts from `SessionProvider` / `WishlistHeartsProvider` (in `app/providers.tsx`) via `useSessionState()` / `useWishlistHearts()`, which return null outside the providers.
- Google, GitHub and enterprise SSO (`docs/superpowers/specs/2026-10-15-oauth-sso-design.md`): the backend Identity module runs the OAuth flow; Next only relays it. `POST /api/auth/oauth/start` (JSON; `provider: "sso"` + `email` picks the SSO connection by domain; `link: true` connects a provider to the signed-in account) returns the provider URL and sets the httpOnly `oauth_flow` cookie (the backend flow id, `next`, intent; `Path=/api/auth`, 10 minutes). Providers return to `/api/auth/callback/[provider]`, which sets the session or redirects to `/account/security?connected=…`; failures redirect with `?error=<code>&provider=<key>`, and pages show fixed text per code (`lib/auth/oauth-errors.ts`), never a message from the URL. Mock mode plays every provider with the `/auth/mock-provider` page (404 in api mode) and an "Acme Corp" SSO connection for `acme.test`. Full-page navigations to a provider go through `navigateTo` (`lib/navigation.ts`) so component tests can mock it.
- Hosting is a mock too: any logged-in user can create listings (`/host/listings/new`); host listings (`hl-` ids, `hostId` = the user id) join `findAll` (only when listed) and `findById` through `combineListings`. Photos come from `PHOTO_OPTIONS` (next/image only allows configured hosts) or, in api mode, are uploads stored as `/api/photos/<id>` (`lib/host/uploaded-photos.ts`): `PhotoUploader` posts to `/api/host/photos` and polls `/api/host/photos/[id]`, `/api/photos/[id]` proxies the processed image, and saving a listing refuses pending, rejected or foreign uploads (`checkUploadedPhotos`). Hosts can't book their own or unlisted listings.
- Listing views (api mode): `/rooms/[id]` renders `ListingViewBeacon` (one `fetch` POST with `keepalive` per page view, a ref guarding strict mode's double effect) unless the viewer is the host; it posts to `app/api/listings/[id]/views` (204 no-op in mock mode, `LISTING_ID_PATTERN` check, then `relayToApi` with `session: false`). Counts come from `getRepositories().listingViews.weekly(id)` (null in mock mode or on failure, logged), and `lib/insights/views.ts` holds the copy (`guestViewsText` on the room page, `hostViewsText` on `/host/listings`). `lib/api/relay.ts` (`relayToApi`) forwards to the backend with the browser IP and, unless `session: false`, the session's bearer.
- Chat (api mode only; `chatEnabled()` in `lib/chat/config.ts`, mockable in page tests): the browser talks to the chat service directly. `lib/chat/connection.ts` (`connectChat`, wrapping `@microsoft/signalr`: WebSockets + `skipNegotiation`, `withAutomaticReconnect`, a fresh token from `GET /api/chat/token` on each connect, hub errors reduced to the server's own words, one handler per hub event registered before `start()`, `onStatusChange` reporting `connected` / `reconnecting` / `disconnected`) is used by `InboxList` and `ConversationThread` through `useChatConnection` (which adds `connecting`; the composer is enabled only when `connected`). Each message carries an `sr-only` sender, and only the other person's new messages reach the `role="status"` region. Components are tested with `fakeConnection()` from `lib/chat/test-connection.ts`. `GET /api/chat/token` relays the session to `POST /api/auth/chat-token` and adds `hubUrl` (`CHAT_HUB_URL`, the gateway). `POST /api/chat/conversations` looks the listing up, refuses your own, and vouches for its host to the chat service with `CHAT_SERVICE_KEY` (`hostIsDemo` = a seed listing); host listings without a profile name their host "Your host". **Message host** sits under the HostCard on `/rooms/[id]` (a login link when signed out).
- Smart chat box (on when `assistantEnabled()` in `lib/assistant/config.ts`: api mode with `ASSISTANT_HTTP`):
  - **Mounting:** `AssistantSlot` in the root layout renders `AssistantChatBox`: the **Ask** button and the panel, with Escape closing it and focus returning to the button. Being in the layout, the conversation survives page navigation.
  - **Asking:** on `/rooms/[id]` each question carries that `listingId`. The history (minus failed answers) is cut to 10 messages of up to 1000 characters, and an answer goes back with a `Places shown: Title (id), …` line for its cards, so a follow-up ("is the first one free?") can look them up.
  - **Rendering:** plain text only (the model's bold marks and heading hashes are stripped). Each turn has an `sr-only` speaker, and the finished answer is announced once in a `role="status"` region.
  - **Transport:** `lib/assistant/client.ts` (`askAssistant`) reads the NDJSON stream line by line (lines can be split across chunks, and unknown events are skipped). `POST /api/assistant` relays to the service with `relayToApi(…, { session: false, timeoutMs: 180000 })` (404 in mock mode, 503 without `ASSISTANT_HTTP`).
  - **Catalog routes:** the public `GET /api/listings/[id]` and `GET /api/listings/[id]/quote?checkIn&checkOut&guests` (the booking rules: `bookingRequestSchema`, `bookingRefusal` (unlisted, guest cap: the one copy, shared with `POST /api/bookings` and `/book/[listingId]`), half-open overlap with `bookings.availability`, `calculatePriceBreakdown`; the quote names the listing's `title`) are the assistant's tools' data.

### Backend Conventions
- Package versions live only in `backend/Directory.Packages.props`; shared settings in `backend/Directory.Build.props` (warnings are errors, so xUnit tests pass `TestContext.Current.CancellationToken`).
- Every `/api` response body and every framework-generated error body is the frontend envelope `{ success, data?, error?, meta?, code? }` (`Airbnb.SharedKernel.ApiResponse`; `code` is a machine-readable failure reason, set only where a client must tell failures apart, e.g. the external sign-in endpoints); `/health`, `/alive`, `/openapi/v1.json` and `/scalar` keep their standard formats. Framework errors are reshaped by `Airbnb.Api/Errors/EnvelopeProblemDetailsWriter`; 5xx messages never carry details.
- Modules: request records are `public` but nested inside `internal` slice classes, and each module calls `services.AddValidation()` in its own `AddXModule`. .NET 10's validation generator ignores `internal` types and only registers types for `AddValidation()` calls in the same assembly.
- Integration tests use `ApiFactory` plus the assembly-wide `InfrastructureFixture` (one Testcontainers Postgres, Redis, AMQP broker, Azurite and Kafka per test run, started in sequence, with every module migrated and seeded once).
- A module lives at `backend/src/Modules/<Name>/Airbnb.Modules.<Name>/`: `<Name>Module.cs` (the only public type — `Add<Name>Module`, `Add<Name>ModuleDatabase`, `Map<Name>Endpoints`), one file per slice (`Query` record + `Handler` + `Map`), `Data/<Name>DbContext.cs` registered through `SharedKernel.Persistence.ModuleDatabase.AddModuleDbContext`, `Data/Migrations/`, `Data/Seed/*.json`. Register a new module in `Airbnb.Api/Program.cs`, `Airbnb.MigrationService/Program.cs`, the tests' `InfrastructureFixture`, and `ModuleRulesTests`.
- Migrations (from `backend/`): `dotnet tool restore`, then `dotnet ef migrations add <Name> --project src/Modules/<M>/Airbnb.Modules.<M> --startup-project src/Modules/<M>/Airbnb.Modules.<M> --output-dir Data/Migrations`. The MigrationService applies them and each DbContext's `UseAsyncSeeding` fills empty tables.
- Seed data is generated, not hand-edited: change `frontend/lib/data/*.ts`, then `npm run seed:export` in `frontend/` (CI runs `npm run seed:check`).
- Queries are cached through `HybridCache` with keys prefixed by the module name and tagged with the module's cache tag.
- The AppHost runs the frontend (`AddJavaScriptApp`, port 3000, `DATA_SOURCE` from `Frontend:DataSource`, default `api`) and the API on its `http` launch profile only. `tests/Airbnb.AppHost.Tests` starts the whole AppHost, so it needs Docker and port 3000 free; CI runs it in its own `apphost` job.
- Cross-module calls go through `*.Contracts` projects (interfaces and records, referencing nothing of ours). A module references SharedKernel and other modules' Contracts only; `ModuleRulesTests` checks exact assembly names.
- Wolverine runs only public handler types, so message handlers live in `Airbnb.Api/Messaging/` and call a module through its Contracts interface; register each such interface with `options.CodeGeneration.AlwaysUseServiceLocationFor<T>()` in `Program.cs`. The review command doesn't use a handler: `SubmitReview` writes through `IDbContextOutbox<ReviewsDbContext>` (review row + event in one transaction).
- Consumers apply a review once per review id: `SharedKernel.Persistence.ReviewStatistics.ApplyOnceAsync` records it in the module's `applied_reviews` table and runs one atomic `UPDATE` in the same transaction, then the module invalidates its cache tag. Raw SQL quotes the PascalCase column names (`"ReviewCount"`).
- Messaging broker: the AppHost picks it with `Messaging:Broker` (`LavinMQ` by default via `CommunityToolkit.Aspire.Hosting.LavinMQ`, which binds host ports 5672/15672; or `RabbitMQ`; anything else fails at startup), always as the resource and connection `messaging`, so the API (`UseRabbitMqUsingNamedConnection("messaging")`: plain AMQP 0-9-1) never knows which; `MessagingBrokerTests` check the switch. Integration tests run the same broker (`cloudamqp/lavinmq`, or RabbitMQ when `MESSAGING_BROKER=RabbitMQ`), readiness by port 5672: the default log check hangs when the host and Docker VM clocks disagree. `new ApiFactory(infrastructure, postgresConnectionString: …, withMessaging: false)` is for tests that point the API at a dead database. Write tests use subjects no read test asserts on (never `l1`/`e1`).
- Notification service (`docs/superpowers/specs/2026-10-28-notification-service-design.md`): Bookings publishes `BookingConfirmed` / `BookingCancelled` (`Airbnb.Modules.Bookings.Contracts`, `[MessageIdentity("booking-confirmed" | "booking-cancelled")]`, camelCase JSON via `UseSystemTextJsonForSerialization`) through `IDbContextOutbox<BookingsDbContext>` to the fanout exchange `bookings`; the booking stores `ListingTitle` (from `ListingBookingInfo.Title`, or the Next quote's optional `title`, else empty). The service (`services/notifications`) has its own copies of both records, listens on `notifications.bookings` bound to `bookings` (durable inbox, Wolverine storage in its `notifications` database, schema `wolverine`; AppHost database resource `notificationsdb`), claims each email in `sent_emails` with `INSERT … ON CONFLICT DO NOTHING` inside the handler's transaction before sending with MailKit to the `mailpit` connection (`Endpoint=smtp://…`), and records the review reminder in `pending_reminders` (due check-out + 1 day 10:00 UTC, in the same transaction; a cancellation marks it), which `DueReminderSweep` sends once due (`Notifications:ReminderSweepInterval`, default 1 minute). Retries: 1 s, 3 s, 10 s, then scheduled 1/5/30 minutes, then the error queue. `POST /reminders/send-due` (`X-Admin-Key` = `Notifications:AdminKey`, 404 without one) sends every waiting reminder; the AppHost exposes it as **Send due reminders now**. Handler-facing types are public (Wolverine compiles its handlers elsewhere) and the Aspire-registered DbContext needs `AlwaysUseServiceLocationFor`. `BookingEventsTests` bind a throwaway queue to `bookings`; the smoke test books `l14` and finds the email in Mailpit.
- Payment service (`docs/superpowers/specs/2026-10-28-payment-service-design.md`): `POST /api/bookings` needs a `card` (`{ number, expMonth, expYear, cvc }`, passed through, never stored). Bookings saves the booking `pending`, then `Payments/PaymentsClient` (named `HttpClient` `payments`, `http://payments`, header `X-Service-Key` = `Payments:ServiceKey`, `Bookings:Payments:AttemptTimeout` default 4 s, 3 attempts; POST retried since the booking id is the idempotency key) charges it: 201 → confirmed + `booking-confirmed` (outbox), 402 → `declined` (`code` `card_declined`/`insufficient_funds`), 400 → `invalid_card` and the pending row is deleted, 401/403 (the two sides disagree on the key) → 503 and the pending row is deleted, no answer → 202 pending. The API refuses to start without `Payments:ServiceKey` (`ApiFactory` sets it). `Payments/PaymentReconciler` (`Bookings:Payments:ReconcileInterval` 30 s, `ReconcilerEnabled`, off in `ApiFactory`) settles pending bookings: succeeded → confirm, declined/voided/refunded → decline, 404 after 2 minutes → decline, unknown after 15 → void then decline. `Booking.Status` is an EF concurrency token, so the request and the reconciler can't both settle one booking. Cancelling a pending booking voids first (503 if the service is down) and publishes nothing; a cancel whose save loses to a confirm starts over in a fresh scope (the old outbox still holds its unsent event) and cancels the now-confirmed booking. Cancel conflicts carry `code` `trip_started` | `payment_declined` | `booking_changed`; the frontend reads only `trip_started` as "already started". The service (`services/payments`): table `payments` (PK `BookingId`; brand + last 4 only), `POST /payments` claims a `processing` row (`INSERT … ON CONFLICT DO NOTHING`) before the `FakeProcessor` (Stripe-style test cards; `Payments:SlowCardDelay` default 10 s) and deletes it on a processor error (503); same booking → the stored outcome, a different amount → 409 `idempotency_conflict`, in flight → 409 `payment_in_progress`; the caller's cancellation is ignored once the processor has the charge; `GET /payments/{id}`, `POST /payments/{id}/void` (one upsert: succeeded or processing → voided, and with no payment yet a `voided` row stays behind, so a late retry gets 409 `payment_voided`); refunds on `booking-cancelled` (queue `payments.bookings`). AppHost: `paymentsdb`, `payments` project, secret parameter `payments-service-key` for it and the API. Booking tests charge through `FakePaymentService` (the `payments` client's primary handler, from `BookingRequests.Factory`); `PaymentFlowTests` run the reconciler with a `MutableTimeProvider`.
- Chat service (`docs/superpowers/specs/2026-10-29-chat-service-design.md`):
  - **Tokens:** the Identity module's `POST /api/auth/chat-token` (session required; mapped only when `Identity:ChatToken:SigningKey` is set, and a key under 32 characters fails at startup) signs a 10-minute HS256 JWT: `iss` `airbnb-identity`, `aud` `chat`, `sub`, `name`. It claims its own rate-limit bucket (`RateLimitBucket.ChatTokens`, `RateLimiting:ChatTokensPerMinute`, default 120), since every chat page and reconnect fetches a token; Next passes a 429 on as a 429. The chat service validates it with JwtBearer (`Chat:TokenKey`, `MapInboundClaims = false`, `access_token` from the query for `/hub`); missing keys fail at startup.
  - **Conversations:** `POST /conversations` (`X-Service-Key` = `Chat:ServiceKey`; only Next calls it, vouching for the listing's host) is idempotent per listing + guest (unique index; a duplicate-key insert returns the winner).
  - **Hub `/hub`** (WebSockets only, `CloseOnAuthenticationExpiration`; `IUserIdProvider` = `sub`): `ListConversations`, `GetMessages`, `Send`, `MarkRead`; events `message` and `read`. Membership is checked on every call ("Conversation not found"); text is trimmed, 1–2000 characters; `SendLimiter` allows `Chat:MessagesPerMinute` (30) per user per instance.
  - **Storage:** MongoDB (`chatdb`, database `chat`; collections `conversations` and `messages`, PascalCase fields, UTC `DateTime`s; no transactions on a standalone server).
  - **Scale:** the Redis backplane (`ConnectionStrings:redis`, channel prefix `chat`) carries `Clients.Users` across the AppHost's two replicas.
  - **Demo hosts:** the first guest message in a `hostIsDemo` conversation claims `AutoRepliedAt` with one conditional update, and `AutoReplies` (an in-memory channel and a `BackgroundService`) answers after `Chat:AutoReplyDelay` (1.5 s).

- Assistant (`docs/superpowers/specs/2026-10-29-assistant-design.md`):
  - **Model:** `services/assistant` answers with the AppHost's Ollama model through `CommunityToolkit.Aspire.OllamaSharp` (`AddOllamaApiClient("assistant-model").AddChatClient().UseAssistantPipeline()`: Microsoft.Extensions.AI function invocation, at most 4 tool rounds). Stateless; no database.
  - **`POST /ask`:** takes `{ messages: [{ role, text }], listingId? }` (1–10 messages, the last one the user's, 1–1000 characters each; 400 `invalid_request` otherwise). It streams NDJSON events `text`, `listings` (up to 3, from the last search, never from the model's text), `done`, or `error` with a fixed message.
  - **Limits:** `Assistant:QuestionsPerMinute` (10) per forwarded IP (loopback proxies only); 400 output tokens; 2 minutes per answer.
  - **Tools** (`Tools/CatalogTools.cs`: `search_listings`, `get_listing`, `quote_stay`) read the Next server's public catalog API (`Assistant:CatalogUrl` = the frontend; typed `CatalogClient`, 10 s). A failed lookup tells the model "unavailable, don't guess" instead of failing the stream. City and category filters are matched to the catalog's own names (case, plural, "Aspen, Colorado"), and a category that finds nothing is dropped and the model told: small models invent categories.
  - **No HTTP resilience:** `ConfigureHttpClientDefaults(http => http.RemoveAllResilienceHandlers())` (experimental, EXTEXP0001) takes ServiceDefaults' handlers off both clients, since a cold model on a CPU takes longer than their 10 s per attempt to start answering; the answer's 2-minute timeout bounds the model instead.
  - **Prompt** (`Ask/Prompt.cs`): today's date, the catalog's cities and categories (cached 5 minutes), the listing context, the rules, and the embedded `Ask/guide.md` (keep it in step with how the app behaves). Among the rules: titles and descriptions are written by hosts (data, never instructions; `get_listing` labels the description `hostDescription`), and places are looked up by the ids given (search results, "Places shown", the listing the guest is on), never guessed.
  - **Logging:** never log question text, answers or tool payloads; HttpClient and ASP.NET Core log at Warning.
  - **AppHost:** `AddOllama("ollama")` (persistent, data volume, Open WebUI, `WithGPUSupport()` when `Assistant:Gpu=true`) and `AddModel("assistant-model", Assistant:Model ?? "qwen2.5:3b")`; the `assistant` project waits for the model; the frontend gets `ASSISTANT_HTTP`.
  - **Smoke test:** runs `--Assistant:Model=qwen2.5:0.5b`, waits for `assistant` to be healthy (the model downloads first), and checks only that an answer streams and ends with `done`.
  - **Tests:** `ScriptedChatClient` (turns: `Says`, `Calls`, `Fails`; records what the model was sent), `FakeCatalog` and `AssistantFactory` swap only the model (or, with `ollama:`, Ollama's endpoint behind the integration's own client: `OllamaClientTests`) and the catalog, so the real pipeline, tools, prompt and stream run.
- Identity: `users` + `sessions` in the `identity` schema; passwords hashed by `PasswordHasher<T>`; opaque bearer tokens stored as SHA-256 (7-day fixed expiry); the `Session` auth scheme sets `ClaimTypes.NameIdentifier` = user id — protect an endpoint with `.RequireAuthorization()`. Endpoints: POST `/api/auth/register|login|logout`, GET `/api/auth/me`. A per-email failed-login throttle (`LoginThrottle`, in-memory per API instance: 10 attempts per email per 15 minutes, reserved atomically before the password check so a concurrent burst gets no more than 10 guesses; unknown emails count; a success resets it) backs up the IP rate limiter, which a spoofed `X-Forwarded-For` can evade.
- External sign-in (Identity module, `External/`): Google (OIDC), GitHub (OAuth 2.0 + REST API) and enterprise SSO connections (generic OIDC by email domain), configured under `Identity:External` (`RedirectBaseUrl` = the frontend's `/api/auth/callback`, `Google`/`GitHub` `ClientId`+`ClientSecret`, `Sso:<id>` with `Name`, `Domains`, `Authority`, client credentials, `RequireHttpsMetadata`); a provider is on when its credentials are set, and bad settings fail at startup. Provider keys are `google`, `github`, `sso-<id>`. Tables `external_logins` (PK provider+subject, unique user+provider) and `external_login_flows` (single-use, 10 minutes, found by the SHA-256 of the flow id; state, nonce and PKCE verifier stay server-side). ID tokens are validated with `Microsoft.IdentityModel` (asymmetric algorithms, issuer, audience, lifetime on `TimeProvider`, nonce). A trusted email links to an existing account only when that account's `EmailVerifiedAt` is set; password registrations never are, so they get `account_exists` and connect from Login & security instead. Endpoints: `GET /api/auth/providers`, `POST /api/auth/external/start|callback`, `GET /api/auth/connections`, `DELETE /api/auth/connections/{provider}` (never the last way in). Provider calls use the named `HttpClient` `identity-external`; `ExternalLoginTests` swaps its handler for `FakeIdentityProviders` (Google, GitHub, Acme). The ServiceDefaults resilience handler doesn't retry POSTs, so a code exchange is never replayed.

- Listing views over Kafka (`docs/superpowers/specs/2026-10-28-listing-views-kafka-design.md`), Insights module (no Contracts project): `POST /api/listings/{id}/views` (ids `l<digits>` or `hl-<guid>`, else 404; own rate-limit bucket via `SharedKernel.RateLimitBucket.Views`, `RateLimiting:ViewsPerMinute`, default 120) produces `{listingId, viewedAt}` keyed by listing id to the `listing-views` topic (3 partitions, `retention.ms=-1`, created at startup by `ListingViewsTopic`) through `Aspire.Confluent.Kafka` (connection `kafka`, idempotent producer, fire-and-forget, 202). `ListingViewsProjection` (consumer group `insights-listing-views`, auto-commit off) batches 500 messages / 1 s and writes `insights.listing_daily_views` plus `insights.consumer_offsets` in one transaction; partitions start from the stored offsets (the assign handler retries that read until the database answers), revoke flushes, loss drops the batch, and a failed write is never retried from memory (the batch is dropped and owned partitions rewound to their stored offsets, since a failed commit may have landed): exactly once. The producer has tracing off, so records carry no `traceparent`. `ListingViewsProjectionTests` drive the projection with `ProjectionHarness` (a fake `IConsumer` that calls the rebalance handlers inside `Consume`/`Close`, a database per test, an EF interceptor that fails commits before or after they land). Kafka's committed offsets are only for Kafka UI's lag. `GET /api/listings/{id}/views` → `{listingId, last7Days, previous7Days}` (HybridCache 5 s + tag `insights`). `POST /api/insights/rebuild` (header `X-Admin-Key` = `Insights:AdminKey`; 404 without a key, 503 when the projection is off) wipes counts and offsets (re-requested on failure) and rewinds to the start; single API instance only; the AppHost exposes it as the **Rebuild view stats** command (`insights-admin-key` parameter). `Insights:Projection:Enabled` (default true) is false in `ApiFactory`; `ListingViewsTests` turn it on and run in sequence. Integration tests run `confluentinc/cp-kafka` (KRaft, readiness by port 9092: log checks fail when the host and Docker clocks disagree). The AppHost runs Kafka + Kafka UI (persistent, data volume); k6's guests post a view per listing.
